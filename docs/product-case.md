# 产品案例

## 背景

个人投资者可能同时使用银行外汇、MetaTrader 和多个分析工具。工具数量增加后，真正消耗时间的并不是查看某一条数据，而是不断切换界面、判断变化是否重要、确认不同来源是否一致。

AUREVAN 的目标不是再增加一个需要用户查看的工具，而是像一位持续工作的投资助理：它盯住工具，把值得处理的事情带到用户面前。

## 角色定位

用户只需要认识 AUREVAN。外汇实盘与 MetaTrader 不作为多个“聊天机器人”出现，而是作为后台的专业分析部门提供数据和结论。

这个定位带来三个直接结果：

1. 用户不需要判断应该问哪个工具；
2. 同一问题不会因为入口不同而丢失账户、品种或工具上下文；
3. 工具能力在后台按统一契约组织，不增加前台使用负担。

产品采用“一个助理 + 多个专业分析部门”的结构。AUREVAN 负责理解、分派、综合和交付；专业部门负责领域数据、计算、规则和原生工作区。二者属于同一个产品与发布体系，但通过进程、数据目录和工具契约保持边界。

## 典型场景

### 场景一：持仓盈利下降

用户问：“我的加元盈利降低了，什么情况？”

系统先识别用户当前持有的加元头寸，读取真实持仓数量、当前估值、盈亏变化和外汇实盘工具的品种分析，再交给模型解释变化原因。回答区分“持仓数量变化”“汇率驱动”和“数据异常”，并明确使用的数据来源。

### 场景二：工具出现异常

工具断开、数据变旧或关键字段缺失时，系统不会把空数据解释为“没有持仓”，也不会继续生成看似完整的报告。它会标记当前数据不可用于决策，并在连接恢复后重新获取有效快照。

### 场景三：用户选择继续观察

用户看到风险提醒后决定暂不操作。系统不会要求用户点击“继续持有”或反复确认，而是保持盯守；只有盈亏、风险线、工具结论或账户状态发生实质变化才再次通知。

### 场景四：逐笔授权 MT4/MT5 交易

用户要求通过 MT4/MT5 执行交易时，系统先固定账户、品种、方向、数量、价格类型和止盈止损，调用终端完成安全预检，再展示结果并请求一次性授权。授权仅匹配这一笔订单，过期或参数变化后必须重新预检；模型、定时任务和失败重试都不能复用授权。

### 场景五：错过授权任务

需要用户授权的定时任务在电脑关闭或用户不在线时不会自动执行。未执行事项保留在待签区域，用户回来后决定执行或撤销；系统不会擅自把条件变化解释为任务自动作废。

## 产品边界

- AUREVAN 提供信息整理、风险提示和辅助分析，不承诺收益；
- 参考行情不用于计算真实持仓和交易风险；
- 不自动交易；MT4/MT5 仅支持经过预检和用户逐笔明确授权的受控执行；
- 模型输出必须以已确认工具数据和用户提供的信息为事实基础；
- 数据不足、数据过期或工具不可用时，系统明确降级，不补造结论。

## 独立完成的工作

- 需求梳理与产品定位；
- 信息架构与核心交互设计；
- 助理、工具、账户和模型之间的系统架构；
- Web 前端、Python 服务、本地数据与 macOS 封装；
- 外汇实盘工具整合、MT4/MT5 统一 Bridge、安全预检与逐笔授权交易链路；
- 测试策略、代码审计、缺陷修复与 README 治理。

## 项目说服力来自哪里

这个项目的重点不是页面数量，而是将产品判断落实为可运行的系统边界：

- **不是普通聊天壳**：用户问题会进入统一上下文、Skill、连接器、数据时效校验和模型分析链路；
- **不是静态仪表盘**：系统持续盯守工具状态与事项变化，并在需要时主动触达；
- **不是模板拼接**：精确事实由本地查询保证，跨工具影响与原因由模型综合解释；
- **不是单工具封装**：外汇实盘与 MT4/MT5 使用统一契约接入，助理层不依赖单一工具实现；
- **不是只做正常路径**：项目对旧数据、空字段、断连、旧进程、跨天数据和重复提醒建立了明确降级规则与测试。

对应的公开证据包括系统架构、数据契约、提醒状态机、脱敏上下文样例和自动化验证记录。

## 代表性工程问题

项目迭代中重点处理过多入口上下文不一致、缺失时间被解释为零持仓、轮询造成重复提醒、桌面旧进程加载旧页面、多 MT4/MT5 终端账户识别，以及专业工具打包后的进程与数据隔离。这些问题分别落实为共享上下文、四态时效契约、事项状态机、启动健康检查、稳定账户身份和专业部门运行标准，而不是仅通过界面提示绕过。
